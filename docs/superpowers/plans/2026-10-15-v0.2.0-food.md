## 1. What v0.2.0 is

When `v0.2.0` is tagged and `release.yml` is green, the people around one person with diabetes can answer "how many carbs is this?" and save the answer as a meal:

- **Lookup** (§4): one call, `lookup(spaceId, query | barcode)`, resolves own library → shared cache → Open Food Facts → Frida → "I know the number". `off` and `frida` are `FoodSource` plugins chosen by configuration; the lookup core never names a plugin; nothing Danish is hard-coded outside the plugins and their configuration.
- **Library** (`Mad` on the phone, `Bibliotek` on desktop): the space's foods with photos and first-class portions, filters, tick-to-verify on the phone, batch verify and an edit panel on desktop, a form for a new food. Anything from OFF, Frida or free text is `verified: false` until an owner or carer ticks it.
- **Log a meal** (`Log et måltid`): scan a barcode with the phone camera or type it (or use a USB scanner) on desktop, search, or pick from favourites and recent; portions as chips; a running total; an optional photo; the carer's "Bolus givet nu" timestamp tap; "Gem måltid". A meal can be corrected or deleted right after saving.
- **simpleMode**: "Hvad spiser du?" shows verified foods only, as photo tiles; "Ja, det spiser jeg" saves the meal. Enforced in the API from the session, not by the client.
- **The viewer's day** (`I dag · ser med`): today's meals and carb totals, no glucose anywhere, enforced in the API.
- **Now** gets its meal regions: "Sidste måltid", "Dagens måltider", the unverified-foods quick link, and the simpleMode "Min mad" tiles.
- Events `meal.created`, `meal.updated`, `meal.deleted`, `food.created`, `food.updated`, `food.verified`, `food.deleted` through `emit()`, live on every device.
- Photos in Blob Storage (originals and thumbnails), metadata stripped, served through short-lived signed URLs.

## 4. Zod contracts (`shared/src/schemas/food.ts`, `meal.ts`, `events.ts`, `api.ts`)

- `Portion = { label: string (1–40), grams?: number (1–5000), carbs: number (0–1000, whole) }`; `FoodOrigin = string matching ^[a-z][a-z0-9-]{0,19}$` with the exported constants `family`, `manual`, `ai`; the UI labels an origin through the message key `food.origin.<id>` ("Fra Open Food Facts", "Fra Frida", "Egen ret") with a generic fallback.
- `Food` (the row), `FoodView` (what clients get: `id, name, carbsPer100g?, portions, barcode?, origin, verified, verifiedBy?, favourite, photo?: { thumbUrl, originalUrl }, updatedAt`); there is no field on `FoodView` that could carry a glucose value.
- `FoodCandidate = { name, carbsPer100g?, portions, barcode?, origin, sourceRef }`: a plugin result not yet in the database. `LookupQuery = { q: string (1–80) } | { barcode: string (8|12|13 digits, valid checksum) }`. `LookupResult = { source: "library" | "cache" | <plugin id>, verified: boolean, food: FoodView | FoodCandidate }`. `LookupResponse = { results: LookupResult[], sources: Record<plugin id, FoodSourceStatus>, manual: { name?: string, barcode?: string } }` — `manual` is step 5, always present, prefilled from the query. `FoodSourceStatus = ok | timeout | error | rate-limited | skipped`.
- `CreateFoodRequest = { name, carbsPer100g?, portions, barcode?, favourite? }` (origin `family` from the library form, `manual` from the log flow: the route decides from `from: "library" | "log"`, never the client's origin); `AddCandidateRequest = { candidate: FoodCandidate }`; `UpdateFoodRequest` (the create fields, all optional); `VerifyFoodsRequest = { foodIds: string[] (1–50) }`.
- `MealItemInput = { foodId?, name, portionLabel?, grams?, carbs? }` — when `foodId` is set and the food has `carbsPer100g` and `grams` is given, the service computes `carbs` with `carbsFor` and ignores a client value; when `portionLabel` names one of the food's portions, that portion's stored carbs are used; otherwise `carbs` is required (manual). `CreateMealRequest = { ts?, items: MealItemInput[] (1–30), note?, bolusTs?, photoDataUrl? }`, `UpdateMealRequest` (all optional, `items` replaces). `MealItemView = { name, portionLabel?, grams?, carbs }` (no `foodId`: a later food delete must not change what a client holds). `MealView = { id, ts, title, slot, totalCarbs, byUser: { id, name }, items, photo?, bolusTs?, note? }`. `DayMealView = MealView minus bolusTs and note`. `DayView = { date, timezone, totalCarbs, mealCount, lastMealAt?, meals: DayMealView[] }`, `.strict()`; a type test asserts its key set, walked recursively, contains none of `mmol`, `mgdl`, `trend`, `reading`, `readings`, `glucose`.
- Events appended to `EventType` and the `EventEnvelope` union: `food.created { foodId, origin }`, `food.updated { foodId }`, `food.verified { foodId, verifiedBy }`, `food.deleted { foodId }`, `meal.created { mealId, ts, totalCarbs }`, `meal.updated { mealId }`, `meal.deleted { mealId }`. All go to `space-<id>` (every member, viewer included): a type test asserts none of the seven payloads has a glucose key, so the viewer's group carries no glucose by construction (v0.1.0 §5).
- `ApiError` codes added in `api.ts`, with a `da` and an `en` message each appended to `web/messages/*.json` by task 1 (v0.1.0's "a message per code" test): `simple-mode` (a write a simpleMode session may not make), `photo-too-large`, `photo-type`, `photo-unavailable` (no photo store configured), `barcode-invalid`, `lookup-unavailable`. Deleting a food is always allowed (it nulls `MealItem.foodId`), so there is no `food-in-use`.

## 5. Lookup resolution (spec §4)

`FoodSource` (`shared/src/food/types.ts`):

```ts
interface FoodSource {
  id: string                       // the plugin id: "off", "frida", "usda"…; also the LookupResult.source tag and the origin
  kind: "remote" | "local"         // remote barcode hits are cached in the shared cache; local results never are
  search(q: string, locale: Locale, signal: AbortSignal): Promise<FoodSourceResult>
  byBarcode(barcode: string, signal: AbortSignal): Promise<FoodSourceResult>
}
type FoodSourceResult = { status: FoodSourceStatus; candidates: FoodCandidate[] }
```

`FoodRepository` (`searchLibrary`, `findLibraryByBarcode`, `searchCache`, `findCacheByBarcode`, `upsertCache`) is the only database access `lookup` has; `PrismaFoodRepository` is real, `MemoryFoodRepository` is the test fake, as `EventSink` is in v0.1.0. `foodSources(env)` builds the plugin list from `FOOD_SOURCES` (a comma-separated list of plugin ids; `.env.example` says `off,frida`; absent or empty means no plugins and the lookup still works from library, cache and manual): a Norwegian deploy changes the setting, not code.

`lookup(repo, sources, { spaceId, session, query, locale })` in `shared/src/food/lookup.ts` returns `LookupResponse` in this order, every result tagged with where it came from, and never branches on a plugin's id:

1. **Own library** (`Food.spaceId = spaceId`): barcode → exact match on the normalised barcode; text → every word of `foldForSearch(q)` is a substring of `nameSearch`, favourites and verified first, then name. Up to 20. From the first character.
2. **Shared cache** (`spaceId = null`): same matching, minus rows whose `sourceRef` already appears in step 1 (the family's copy wins). Up to 10. From the first character.
3. **Open Food Facts** and 4. **DTU Frida**: every registered source, in `FOOD_SOURCES` order, in parallel with a 2.5 s timeout each; text only from three characters, otherwise `skipped`. A source that fails, times out or is rate-limited contributes nothing and reports its status in `sources`; steps 1 and 2 never wait beyond that timeout. A barcode hit from a `remote` source is upserted at once into the shared cache (`spaceId = null`, `origin = source.id`, `verified = false`, `sourceRef = <id>:<barcode>`), because the next family scanning the same product should not call the source again; text results are cached only when picked.
5. **Manual**: always present as `manual: { name?: q, barcode? }`; the UI renders it as "Jeg kender tallet selv · Opret "{q}" med dine egne tal".

Rules: a session with `simpleMode` gets step 1 filtered to `verified = true` and steps 2–4 `skipped`: `simpleMode` shows verified foods only (§2), enforced here from the session, not from a client flag. The `viewer` role never calls `lookup` (403 in the route). Remote text search is triggered by an explicit submit (Enter or the search button), not per keystroke: OFF allows at most 10 searches per minute per IP, and the whole app shares one IP; library, cache and `local` sources update as the user types.

Picking a candidate (`POST foods { candidate }`) creates the space's own copy: `spaceId = spaceId`, `origin` and `sourceRef` kept, `verified = false`, `createdBy = session.userId`, idempotent on `(spaceId, sourceRef)`; it emits `food.created`. Verification always acts on a space-owned row; the shared cache is never verified, because a tick is one family's judgement.

## 6. Photos (spec §4 "Photos", §1 Blob Storage)

- `PhotoStore` (`shared/src/photos/types.ts`): `put(key, { original, thumb })`, `delete(key)`, `readUrl(key, size)`. `blob.ts` implements it against a private container `photos` with a connection string (Static Web Apps has no usable managed identity, v0.1.0 decision 10) and returns SAS read URLs signed server-side, expiring at the next full hour plus one hour (so a URL is stable within the hour and the browser caches the thumbnail); the account key never reaches a client. `memory.ts` is the test and seed fake. Without `BLOB_CONNECTION_STRING` (local dev without Azurite, PR tests), photo routes answer 503 `photo-unavailable` and everything else works.
- `process.ts` (sharp): apply EXIF orientation, then re-encode as JPEG with **no metadata** (EXIF, GPS, ICC dropped: a lunchbox photo must not carry a location), original at most 1600 px on the long side, quality 82; thumbnail 320×320 cover (the largest tile is 140 px at 2× DPR). Input limit 8 MB; the server accepts `image/jpeg`, `image/png`, `image/webp` only (sharp's prebuilt libvips does not decode HEIC); the client's `downscale.ts` draws the picked file onto a canvas (Safari decodes HEIC there), resizes to 1600 px and uploads JPEG, so an iPhone photo never reaches the server as HEIC.
- Keys: `spaces/<spaceId>/foods/<foodId>/<random>` and `spaces/<spaceId>/meals/<mealId>/<random>`, stored as `photoKey`; `readUrl` appends `/original.jpg` or `/thumb.jpg`. Deleting a food or a meal deletes its blobs after the database write succeeds (best effort, logged by key count only). A photo is stored only when the user saves the food or the meal, never on a preview.
- Infra (task 2): `infra/modules/photos-storage.bicep`, Standard LRS, `allowBlobPublicAccess: false`, `minimumTlsVersion: TLS1_2`, blob soft delete 7 days, container `photos`, tagged `project=frejsi`; `infra/main.bicep` appended, `main.bicepparam` updated; `deploy.sh` creates the Key Vault secret `blob-connection-string` once if absent (as it does for Web PubSub) and writes the SWA app setting `BLOB_CONNECTION_STRING`; `infra/README.md` adds the resource and its cost line. Local dev uses Azurite with the same adapter (`docs/operations.md`, task 10); tests use `MemoryPhotoStore`.
- Risk named for the release: `sharp`'s `@img/sharp-linux-x64` binary must land in the standalone Next.js bundle on Static Web Apps. Task 10 checks the built app processes a photo; the fallback, if it cannot, is server-side storage of the client-downscaled JPEG as both original and thumbnail (the client already strips metadata by re-encoding through a canvas), decided by the lane and recorded in `docs/operations.md`.

## 7. API routes and services

All under `web/src/app/api/spaces/[spaceId]/`; every handler starts with `requireRole` (v0.1.0 §6), delegates writes to `web/src/lib/foods/` or `web/src/lib/meals/` (so the seed reuses them, as v0.1.0's seed reuses `web/src/lib/auth/`), and every write ends with `emit`. Log lines carry `spaceId`, `userId`, ids, counts and codes only: never a food name, a barcode, a query, a photo or a meal note.

| Route | Roles | Behaviour |
|---|---|---|
| `GET foods?filter=all\|unverified\|own\|favourites\|recent\|<origin>&q=` | owner, carer | the space's foods as `FoodView[]` with counts per filter; `recent` = foods of the last 30 days' meal items, newest first; a simpleMode session gets `verified = true` only |
| `POST foods` | owner, carer | create from fields (`origin = family` for `from: "library"`, `manual` for `from: "log"`) or from a `candidate`; always `verified = false`; emits `food.created`. With `verify: true` (the desktop "Gem og godkend") the service then verifies in the same request and emits `food.verified` too: two writes, two events |
| `GET/PATCH/DELETE foods/[foodId]` | owner, carer | PATCH emits `food.updated`; DELETE nulls `MealItem.foodId`, deletes the photo, emits `food.deleted` |
| `POST foods/verify { foodIds }` | owner, carer (not a simpleMode session) | sets `verified, verifiedBy = userId, verifiedAt`, emits `food.verified` per food |
| `PUT/DELETE foods/[foodId]/photo` | owner, carer | processes and stores, sets `photoKey`, emits `food.updated`; 503 `photo-unavailable` without a store |
| `GET lookup?q=\|barcode=` | owner, carer | §5; 400 `barcode-invalid` for a bad checksum |
| `POST meals` | owner, carer | computes item carbs and the total, `byUserId = session.userId`, `ts` defaults to now, `bolusTs` accepted only from a non-simpleMode session (else 400 `simple-mode`), optional photo, emits `meal.created` |
| `GET/PATCH/DELETE meals/[mealId]` | owner, carer | GET returns `MealView`; PATCH replaces items and recomputes, emits `meal.updated`; DELETE emits `meal.deleted` and deletes the photo |
| `PUT/DELETE meals/[mealId]/photo` | owner, carer | as for foods; emits `meal.updated` |
| `GET day?date=YYYY-MM-DD` | owner, carer, **viewer** | `DayView` for the space's local day (`dayRange` with `Space.timezone`); default today; no `bolusTs`, no note, no glucose; the only meal read a viewer may call. Every other route in this table answers 403 to a viewer |

## 8. Test strategy (extends v0.1.0 §8)

- Unit tests with vitest next to the code; every acceptance criterion below has one; `pnpm -r test` still needs no network, database, browser or Azure. `lookup` is tested with `MemoryFoodRepository` and `FakeFoodSource`; routes with the memory fakes behind `FoodRepository`, `PhotoStore` and `EventSink`; screens with `@testing-library/react` and a fetch fake that serves the Zod contracts, so a screen lane and its API lane can build in the same wave.

## 11. Decisions taken by the planner

Each is a choice the spec or the design left open, with the reason. The owner can veto any of them by opening a `needs-owner` issue.

1. **The "Bolus givet nu" tap is in v0.2.0**, not v0.3.0 as the roadmap first said: the Log-Portioner and Log-Desktop artboards draw it on the log screen, the timestamp must be captured when the meal is logged, and `bolusTs` is in §2's `meals`. v0.3.0 draws it on the curve. It is a timestamp and nothing else; the drawn sentence ("… så det kan ses på kurven …") is kept as drawn although the meal line on the curve arrives in v0.3.0, and its `en` counterpart is quoted in §8 so the allow-list change is reviewed here, not invented by a lane.
2. **Portions store their carbs** (`{ label, grams?, carbs }`) and `carbsPer100g` is optional: a dish like "Min madpakke · 42 g" has no per-100 g value and must still be a food; "Vej det" appears only when the per-100 g value exists.
3. **`favourite` is a column on `Food`** with a "Favorit" toggle in the edit form: the artboards separate "Favoritter" from "Spist for nylig"; "recent" is derived from meal items (last 30 days) and needs no column.
4. **`nameSearch` is a folded copy of the name** and search is substring-per-word over it: SQL Server's default collation is accent-sensitive, and the folding is generic Latin (NFD plus a map for letters without a decomposition), not a Danish rule. Semantic search is v0.4.0.
5. **`FoodSource` carries `id` and `kind`**, `origin` is a validated string rather than a closed enum, and the lookup core caches by `kind`, tags results by `id` and never names a plugin; `FOOD_SOURCES` switches plugins on. A `usda` plugin is one folder, two appended lines and a setting.
6. **Shared cache holds remote barcode hits**, written at lookup time, and picked text results; `local` sources (Frida) are never cached; text results are never written at lookup time (ten rows per keystroke would flood the table).
7. **A pick copies the candidate into the space library** (`origin` and `sourceRef` kept, `verified: false`, idempotent on `(spaceId, sourceRef)`); verification acts on the space copy only. The shared cache is never verified: a tick is one family's judgement.
8. **Shared cache writes do not emit**: `spaceId` is null, so there is no space and no listener; the rule "every write to space data emits" is kept literally, and the cache write is the only write `lookup` can make (asserted).
9. **Creation is always `verified: false`, even from the carer's own form**; "Gem og godkend" is create then verify in one request with two events, so the hard rule holds without an exception for free text.
10. **`sourceRef` is required and `(spaceId, sourceRef)` is unique**: SQL Server treats NULLs as equal in a unique index, so typed foods get `family:<id>` / `manual:<id>` and no filtered index is needed. The `Space`/`User` relations are `NoAction` because of SQL Server's multiple-cascade-path rule.
11. **Verification and food writes are gated by role (owner, carer), not by `simpleMode`**, except that a simpleMode session cannot verify or set `bolusTs` (400 `simple-mode`) and is redirected from `library` and `log` to the simple screens: simpleMode is a presentation setting (§2), and the two server-side refusals cover the only writes that would matter.
12. **simpleMode filtering is server-side from the session** in `lookup`, `GET foods` and therefore `eat`; no client flag can widen it.
13. **Remote text search runs on submit, not per keystroke**, with a token bucket of 10 searches and 100 product reads per minute per process in the OFF adapter: OFF's published limits apply per IP, and every family shares the app's IP. Library, cache and local sources update as the user types, from the first character.
14. **OFF country and language are configuration** (`OFF_COUNTRY`, the user's locale), so a Norwegian deploy changes a setting, not code. OFF text search uses the legacy `cgi/search.pl` endpoint (the v2 API has no free-text search).
15. **Frida ships as a generated JSON in the repo** (`shared/src/food/frida/data/frida.json`, bundled into the deploy), produced by a checked-in importer from a CSV export of the DTU sheet, not loaded into the database at deploy: the plugin stays a `FoodSource`, lookups need no DB rows for Frida, and "imported at deploy time" is met because nothing is fetched from DTU at runtime. The importer takes **available carbohydrate (excluding fibre)**, the figure carb counting uses. The lane records the licence and attribution; if the licence does not allow redistribution, the lane keeps the dataset out of the repo and `release.yml` generates it at build time.
16. **OFF product names are "{product_name_<lang> | product_name}, {brand}"** with no normalisation: the normalisation ("Rugbrød, Schulstad Det Gode") is the v0.4.0 AI step.
17. **OFF images are not fetched or stored**: their CC BY-SA licensing needs attribution the screens do not show; the family's own photo is what makes simpleMode work.
18. **Photos are private blobs behind SAS read URLs** issued by the API and signed with the account key from an app setting, expiring at the next full hour plus one so URLs are cacheable within the hour: Static Web Apps has no managed identity (v0.1.0 decision 10), and a public container would expose a child's lunchbox to anyone with a URL.
19. **Every photo is re-encoded with all metadata stripped** (EXIF, GPS, ICC) and the orientation applied: a phone photo carries a location, which is PII. HEIC is converted on the client (sharp cannot decode it); the server accepts JPEG, PNG and WebP.
20. **Thumbnails are 320×320 JPEG**, originals at most 1600 px: the largest tile is 140 px at 2× DPR; the client downsizes before upload to spare the phone's network.
21. **A separate Standard LRS storage account for photos**, not the Function App's: Functions want their account to themselves, and the spec's resource table lists Blob Storage as its own line. Without a store configured, photo routes answer 503 `photo-unavailable` and the rest works.
22. **Local photo development uses Azurite** with the same adapter; no disk adapter, so there is one real code path. The seed stores no photos, so the release e2e needs no blob store.
23. **`sharp` on Static Web Apps is a named release risk** with a stated fallback (store the client-downscaled JPEG as both sizes); `shared` exposes `photos` and `food` as subpath exports so the poller bundle never pulls `sharp`.
24. **Meal titles are derived** (`note` when present, else the item names joined with `Intl.ListFormat` for the locale) and the meal slot (Morgenmad/Frokost/Aftensmad/Mellemmåltid) is an i18n key chosen from the local hour; no title column.
25. **Item carbs are whole grams, rounded half up**; `carbsPer100g` keeps one decimal: that is how carbs are counted at the table and how the artboards show them. UPC-A barcodes are normalised to EAN-13 so the cache holds one row per product.
26. **The day is the space's local day** from `Space.timezone`; no timezone constant anywhere (`@date-fns/tz` may be used).
27. **`DayView` carries no `bolusTs` and no note, and `MealItemView` no `foodId`**: a viewer (a teacher, a club) needs meals and carbs, nothing else; carers see the meal's own fields on `GET meals/[id]`; and a food delete must not change what a client holds.
28. **Meal events go to the viewer's group**: they carry ids, a timestamp and a carb total, no glucose, so the viewer's day can be live.
29. **Meals can be corrected right after saving** by reopening the log screen (`?meal=`) with "Slet måltid"; the "Sidste måltid" card and the Nu-Desktop rows point there in v0.2.0 and v0.3.0's meal detail takes those entry points over. A parent who tapped "2 skiver" for one slice must be able to fix it today.
30. **"Sig det" / "Sig det i stedet", "Tag et billede" in simpleMode, "Spørg en voksen", the OFF-contribution checkbox, the "Top" column and "Ugens opsummering" are omitted, not drawn disabled**, as v0.1.0 did with its placeholders: they belong to v0.3.0–v0.5.0. "Noget andet?" in simpleMode becomes a search over the verified list until v0.4.0.
31. **Barcode detection uses `zxing-wasm` (self-hosted) with `BarcodeDetector` where the browser has it**: iOS Safari has no `BarcodeDetector`, and the family's phones are iPhones; checksums are validated before any lookup; an unknown barcode lands on "Jeg kender tallet selv" with the barcode prefilled, so the supermarket case never dead-ends.
32. **A desktop field value of 8, 12 or 13 digits with a valid checksum plus Enter is a barcode**: that is what a USB scanner types, and the spec wants the same field to serve both.
33. **`useLiveFeed` grows an additive event subscription** in task 8, the first consumer, so screens keep reading only from the hook (§3b) and the v0.1.0 tests stay untouched.
34. **Services, not routes, write**: `web/src/lib/foods/` and `web/src/lib/meals/` are the only food and meal writers, as `web/src/lib/auth/` is for members in v0.1.0, so the seed and the routes share one path and the lint boundary is checkable.
35. **Screen lanes and API lanes build in the same wave** against the Zod contracts with a fetch fake, so the milestone has one short critical path (contracts → screens and routes → Now wiring → release).
36. **Copy the plan adds** because no artboard has it: "Ingen måltider i dag endnu" (Now and the viewer's day), "Biblioteket er tomt endnu", "Skriv stregkoden", "Slet måltid", "Favorit", "Noget andet?" as a search, "Der er ingen tjekket mad endnu – bed en voksen om at tjekke noget mad i biblioteket", "Måltidet blev ikke gemt – prøv igen", "Det blev ikke gemt – prøv igen", "Kunne ikke gemme – prøv igen", "Ingen forbindelse lige nu", "Open Food Facts svarer ikke lige nu", the `simple-mode`, `barcode-invalid`, `photo-*` and `lookup-unavailable` error messages, and every `en` string. The copy-reviewer may rephrase.
37. **`Space.subjectUserId` stays null**: nothing in v0.2.0 needs it; the picker shows the space's verified foods and simpleMode comes from the session.
38. **No decision tasks**: every open question had a safe default a lane can build on (see §12).
