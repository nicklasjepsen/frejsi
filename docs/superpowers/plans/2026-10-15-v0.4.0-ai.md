## 1. What v0.4.0 is

When `v0.4.0` is tagged and `release.yml` is green, a space whose owner has switched "AI-hjælp" on gets four things, and a space that has not is exactly v0.3.0 (its data never reaches a model, not even for embeddings):

- **Search that understands food** (§5.1). On submit, "det brune brød" finds Rugbrød in the family's library and the shared cache through embeddings stored on `foods` (Azure SQL `vector(1024)`), own library still above cache above Open Food Facts. OFF's product names are normalised once, shortly after a candidate is picked or cached ("SCHULSTAD DET GODE RUGBRØD 950G" → "Rugbrød, Schulstad Det Gode" with suggested portions), by the small model, and never again.
- **"Sig det"** (§5.2). An owner or carer speaks or types "to skiver rugbrød med ost og et æble"; the model calls `lookup()` as a tool per item and returns a structured meal; the person confirms it line by line and saves it through the existing meals API. Voice through the Web Speech API on top; nothing is sent to Frejsi's provider until the person taps "Find maden".
- **Photo → estimate and "Spørg en voksen"** (§5.3). In simpleMode "Noget andet? · Tag et billede" takes a plate photo; the estimate is shown as `Maaltid-Simpel` draws it ("Det ligner", "Et gæt · ikke tjekket", "ca. 50 g", "Det er et gæt. En voksen skal kigge på det, før du bruger tallet."); "Spørg en voksen" saves the dish as an unverified `ai` food with the photo and pushes to the carers' phones, who correct and tick it in the library. Adults get the same estimate inside the "Sig det" sheet.
- **Insight as observation** (§5.4). One sentence on meal detail, labelled "Observation · AI · ud fra tallene, ikke et råd", narrating the statistics v0.3.0 computes in code; the weekly "Ugens opsummering" with "Spørgsmål til klinikken", generated Sunday evening by the poller, editable and copyable. The model receives statistics only, never a reading.
- **The hard rules as code**: `AiProvider` is the only way to a model; every call runs through one capped, logged provider per space (`AI_DAILY_CAP`, default 50); the output schemas have no field that could carry insulin, and the dosing-vocabulary test runs on every prompt file and on every string a model returns; raw readings cannot reach the AI code (lint boundary); photos and text leave the device only on a tap; everything the AI produced is `verified: false` or labelled "Et gæt" until a human acts.
- **Settings** (`Indstillinger`): the "AI-hjælp" row and section, on/off and provider per space, the drawn notices and "Højst 50 kald om dagen i dette rum. I dag: 7.".
- **Evals** under `evals/`: ~30 Danish free-text messages with expected parses, the harness and case format for ~50 Danish meals with known carbs (photos and weighed values come from the owner), and insight cases; scored against fixed thresholds; run in PR CI only when `evals/`, `shared/src/ai/` or `web/src/ai/` change (`ci.yml` already filters on those paths) and in full at every release.

## 4. Zod contracts (`shared/src/schemas/ai.ts`)

All `.strict()`. A type test asserts that the key set of every schema in this file, walked recursively, contains none of these words, matched word-bounded on camelCase parts and case-insensitive: `insulin`, `dose`, `dosing`, `ratio`, `correction`, `bolus`, `icr`, `isf`, `suggest`, `advice`, `recommend` (the bare `unit`/`units` are not on the list, as in v0.1.0 decision 29: `glucoseUnit` is the existing settings key), and the dosing-vocabulary test (v0.1.0 §8) keeps walking the schema keys and enum values through `shared/src/schemas/index.ts`.

- `AiProviderId = anthropic | azure-openai | ollama`; `ModelRole = small | everyday | insight | embed` (decision 1). Nothing outside the adapters names a model id.
- `EstimatedItem = { name: string (1–120), grams?: number (1–2000), carbs: number (0–500, whole), confidence: low | medium | high, approx: true }` — the one item shape both the parse and the photo paths produce for anything the model guessed. `approx` is a literal `true` so a client cannot render an estimate as an exact value.
- `ParsedMeal = { items: ParsedItem[] (0–12), unmatched: string[] (0–12) }` (no free-text note: nothing renders one); `ParsedItem = { query: string, match?: { source: "library" | "cache" | <plugin id>, food: FoodView | FoodCandidate, portionLabel?: string, grams?: number }, estimate?: EstimatedItem }` with the refine "exactly one of `match`, `estimate`". `match` is a `LookupResult` the tool returned, chosen by the model; `estimate` is a typed guess when nothing matched. There is no `verified` on a `FoodCandidate` (v0.2.0 task 3) and `match.food.verified` is whatever the library row holds.
- `PhotoEstimate = { items: EstimatedItem[] (1–10), totalCarbs: number (whole), dishName: string (1–80), approx: true }`.
- `NormalisedFood = { name: string (1–120), portions: Portion[] (0–4) }` (v0.2.0's `Portion`).
- `InsightStats = { peak?: { mmol: number, minutesAfterMeal: number }, inRange: InRange, leadMinutes?: number, readingCount: number }` and `InsightNumbers = { inRangePercent?, previousWeekInRangePercent?, belowPercent?, lowEpisodes: { count, atNight }, carbsPerDay, mealCount, lead: { meanMinutes?, registered, of } }` — v0.3.0's `MealStats` and `WeekNumbers` **re-shaped for the model**: `peak.ts` dropped (no timestamp series), `bolusLeadMinutes` → `leadMinutes` and `bolusLead` → `lead` ("minutes between the carer's time tap and the meal"), so the serialised input contains no dosing word and the §4 key test passes. Only `shared/src/ai/insight/input.ts` builds them, from `MealStats`/`WeekNumbers` values, and accepts no other type.
- `InsightInput = { locale, glucoseUnit, meal: { title, totalCarbs, slot, localTime }, stats: InsightStats, previous: { localDate, totalCarbs, stats: InsightStats }[] (0–5), leadLabel: "before" | "after" | "none" }`; `WeekInsightInput = { locale, glucoseUnit, isoWeek, weekStart, numbers: InsightNumbers, days: { localDate, mealCount, totalCarbs, inRangePercent? }[] (7), meals: { localDate, localTime, title, totalCarbs, peak?: { mmol, minutesAfterMeal }, inRangePercent?, leadMinutes? }[] (0–40) }`. Neither has a `readings` key nor any array of numbers (type test). Meal titles are family-typed dish names; no person's name or id is in either input.
- `MealInsight = { text: string (20–280) }`; `WeekInsight = { summary: string (20–600), questions: string[] (0–5, each 10–240) }` — the model's structured outputs; the only output schemas any provider call may ask for, apart from `ParsedMeal`, `PhotoEstimate` and `NormalisedFood`.
- `MealInsightView = { state: "ready" | "pending" | "off" | "cap" | "unavailable", text?, createdAt?, model? }`; `WeekInsightView = { state, summary?, questions?, questionsEdited, rejectedCount, createdAt?, readyAt?: ISO datetime (Sunday 18:00 local for the current week) }`. Owner/carer only, like every history view.
- `AiUsage = { enabled: boolean, provider?: AiProviderId, providers: { id: AiProviderId, configured: boolean, capabilities: { complete, vision, embed } }[], callsToday: number, dailyCap: number, embedCallsToday: number, embedDailyCap: number, pushPublicKey?: string }` — `pushPublicKey` is served at runtime because `NEXT_PUBLIC_*` values are inlined at build time, before `deploy.sh` runs (decision 23).

## 5. The provider boundary (spec §5 "one interface, several providers" and the hard rules)

`AiProvider` (`shared/src/ai/types.ts`), provider-neutral so that the three adapters, the fake and the capped wrapper all implement it:

```ts
interface AiProvider {
  readonly id: AiProviderId | "fake" | "capped"
  complete(req: { role: ModelRole; system: string; messages: AiMessage[]; tools?: ToolDefinition[]; outputSchema?: z.ZodType; maxTokens?: number }): Promise<CompleteResult>
  vision(req: { role: ModelRole; system: string; image: { mediaType: "image/jpeg"; base64: string }; prompt: string; outputSchema: z.ZodType }): Promise<CompleteResult>
  embed(req: { texts: string[] }): Promise<{ vectors: number[][]; model: string }>   // 1024 dimensions, or throws NotConfigured
  capabilities(): { complete: boolean; vision: boolean; embed: boolean }
}
type CompleteResult = { kind: "json"; json: unknown; model: string } | { kind: "tool-calls"; calls: ToolCall[]; model: string } | { kind: "text"; text: string; model: string } | { kind: "refusal"; model: string }
```

- **Roles, not ids.** The anthropic adapter maps `small` → `claude-haiku-5-5`, `everyday` → `claude-sonnet-5-5`, `insight` → `claude-fable-5-1`, `embed` → Voyage `voyage-3.5` at 1024 dimensions (decisions 1, 2); azure-openai maps the roles to the deployment names in `AZURE_OPENAI_DEPLOYMENT_SMALL`, `_EVERYDAY`, `_INSIGHT`, `_EMBED` (default `text-embedding-3-small` with `dimensions: 1024`); ollama to `OLLAMA_MODEL_SMALL`, `_EVERYDAY`, `_INSIGHT`, `_EMBED` (default `mxbai-embed-large`, 1024). The call sites say what they need (`role: "everyday"`), never which model. Per-role timeouts: 20 s `small`, 30 s `everyday`, 120 s `insight`, 10 s `embed`.
- **Anthropic API usage** (`@anthropic-ai/sdk`, verified against the `claude-api` skill on 2026-10-15): `client.messages.create` with `output_config: { format: zodOutputFormat(schema) }` for every structured output (never assistant prefill, which these models reject); `tools` with `strict: true` and `tool_choice: { type: "auto" }` only — forced `any`/`tool` returns 400 on Claude Sonnet 5.5 and Claude Fable 5.1; no `thinking` parameter is sent (adaptive by default on all three models; `budget_tokens` is rejected); `output_config.effort` `low` for `small` and for `everyday` parse, vision and normalisation, `medium` for both insights (the weekly runs in the poller, where there is no request timeout; its output is six short lines); `max_tokens` 4096; non-streaming; `stop_reason === "refusal"` becomes `{ kind: "refusal" }` (decision 8); typed SDK errors (`RateLimitError`, `APIConnectionError`, `APIError`) are mapped to `ai-unavailable` with the class name only in the log. Images go as `{ type: "image", source: { type: "base64", media_type: "image/jpeg", data } }` before the text block. Fable 5.1 requires 30-day data retention (§13).
- **The tool loop** (`shared/src/ai/tool-loop.ts`) is ours and provider-neutral: `runToolLoop(provider, req, tools, { maxCalls: 8 })` repeats `complete` while the result is `tool-calls`, runs each tool in parallel, appends every result in one message, and stops with the final `json`. The same loop drives the three adapters and the fake, so parse is tested without a network and the azure-openai and ollama adapters need no SDK helper.
- **The cap, the validation and the string guard live in one wrapper** (`shared/src/ai/capped.ts`): `CappedAiProvider(inner, calls, { spaceId, userId, dailyCap, embedDailyCap, timezone, now })` counts `complete` and `vision` against `AI_DAILY_CAP` (default 50) and `embed` against `AI_EMBED_DAILY_CAP` (default 500) per space per **local** day (`Space.timezone`, v0.2.0's `dayRange`; UTC for `spaceId: null`), refuses with `ai-cap-reached` **before** calling the inner provider, records one `AiCall` row per attempt (ok or not), validates every `json` result against the request's `outputSchema`, and runs `assertNoDosing` over **every string field** of the validated output (`EstimatedItem.name`, `dishName`, `NormalisedFood.name`, the insight texts and questions) so no model-written string reaches a screen, a `Food.name` or a push body unguarded. `aiForSpace(spaceId, session)` in `web/src/ai/provider.ts` is the only constructor of a usable provider in `web/`: it loads the space, throws `ai-disabled` when `aiEnabled` is false, `ai-not-configured` when the registry has no adapter with keys for `aiProvider`, and returns the capped provider. The poller's two timers construct capped providers the same way through the registry: per space with that space's provider and caps, and with `spaceId: null` and `AI_EMBED_BACKFILL_DAILY_CAP` (default 2000) for the shared cache. The evals wrap the live adapter in the same class with `MemoryAiCallRepository` and a run cap of 200.
- **The dosing guard** (`shared/src/ai/guard.ts`): `assertNoDosing(text, where)` runs v0.1.0's `findDosingVocabulary` with the full list and **no allow-list** (generated text cannot be enumerated) and throws `ai-rejected` on a hit. `shared/src/ai/prompts.test.ts` runs it on the content of every `prompt*.ts` under `shared/src/ai/` and asserts the number of files it found equals a directory listing, so it never passes vacuously. `shared/src/dosing.test.ts` (v0.1.0) gains one case that imports the prompt files and the accepted outputs under `fixtures/ai/insight/`, so the single required CI step "Dosing vocabulary test" covers generated text and prompts as the spec asks. The retry-then-reject path is tested by scripting a sentence with a listed word through `FakeAiProvider`, not by a fixture inside the walked glob.
- **The raw-readings boundary** is structural, not a prompt instruction: `InsightStats`/`InsightNumbers` are built from `MealStats`/`WeekNumbers` values by `input.ts`, which accepts nothing else; the lint boundary of §2 keeps `Reading`, `readingsBetween`, `HistoryRepository`, `prisma.reading`, `shared/src/glucose/`, `week-input.ts` and `web/src/lib/history/` out of `shared/src/ai/` and `web/src/ai/`; the insight route calls history itself and hands the service `stats`, `previous[].stats` and the meal's title, carbs, slot and time, never `MealCurveView`; the poller's `weekly-insight` builds `WeekInsightInput` through `shared/src/insights/week-input.ts` and hands the AI service that object only. A test serialises the input built from `fixtures/curves/meal-typical.json`'s stats and asserts it contains no reading value and no timestamp. The peak value ("top 9,6 efter 1 time") is a statistic the design's own notice names.
- **The explicit-action boundary**: `parse` and `estimates` are `POST` routes called only from a tap ("Find maden", the camera shutter in `ask` and in the Say sheet). The Web Speech transcript fills the field and is never sent to Frejsi's provider on `speechend`; the browser's own speech service is a third party outside Frejsi's provider choice (Chrome sends audio to Google; Firefox has no `SpeechRecognition`), stated in the Settings notice and `docs/operations.md` (decision 15). v0.2.0's "Vedhæft billede" / "Tag et billede" on the confirm screen attaches a meal photo and never calls `estimates` (page tests record the fetch calls). Search embeddings are sent on submit (`remote: true`), never per keystroke. **A space with `aiEnabled: false` sends nothing anywhere**: the enrichment timer skips its rows (task 5).
- **Unverified**: a parsed item that matched a candidate is copied into the library through v0.2.0's `addCandidate` (`verified: false`) when the person confirms; a guessed item becomes a typed meal item labelled "ca." and creates no food; "Spørg en voksen" creates an `origin: ai` food `verified: false` through the same `addCandidate` with `sourceRef: ai:<id>`; a normalised OFF name lands on a cache row or a space copy that is unverified already. Nothing in v0.4.0 sets `verified`.

## 7. Semantic search, normalisation and embeddings (spec §5.1)

- **One poller timer, `enrich-foods`, every 15 minutes, normalises first and embeds second** (task 5), so a vector is always of the final name. Step 1: up to 50 rows with `origin` ∈ the registered `remote` plugin ids and `sourceName IS NULL` (cache rows first; a space row is normalised only when its space has `aiEnabled`): `normaliseFoodName` (`role: small`, the user-independent `da` locale for cache rows, the space's owner's locale for space rows) → `name`, `portions` where the row had none, `sourceName` = the original; a space copy of the same `sourceRef` whose `name` still equals the original gets the same name and emits `food.updated`; a cache row emits nothing (v0.2.0 decision 8); a failed or capped call writes `sourceName = name` so the row is never retried. `origin: ai` rows and typed rows are never normalised (rule). Step 2: up to 100 rows whose `embedding` is null or whose `embeddingModel` differs from the model their provider produces, **grouped by provider**: rows of a space with `aiEnabled` through that space's provider and embed cap; cache rows (`spaceId null`) through the deployment's `AI_CACHE_EMBED_PROVIDER` (default: the first configured adapter) and the backfill cap; rows of a space with `aiEnabled: false` are **skipped** (nothing of theirs reaches a model, §1). One `embed` call per batch; `FoodRepository.setEmbeddings` with `$executeRaw`. `web/src/lib/foods/` nulls `embedding`/`embeddingModel` on a name change, so a renamed food is re-embedded within the quarter hour and is found by keyword meanwhile. Without an adapter that can embed, the timer logs `code: ai-not-configured` once per run and exits (decision 3). A space on a provider other than `AI_CACHE_EMBED_PROVIDER` searches the cache by keyword only (its query vectors and the cache's vectors are in different spaces); stated in `docs/operations.md`.
- **`addCandidate` keeps v0.2.0's signature** and makes no AI call: the meal-save path stays fast and key-free (decision 3), and task 7 calls it in the same wave unchanged. The user sees the plugin's raw name for up to a quarter hour; the cache row is normalised once for every family (decision 18).
- **`lookup` gains a semantic pass** (`shared/src/food/lookup.ts`, optional `embed?: (q) => Promise<number[] | null>` in its deps): on `remote: true` and `q` of three characters or more, `embed(q)` once, then `repo.searchLibrarySemantic(spaceId, vector, model, 20)` and `repo.searchCacheSemantic(vector, model, 10)` (`VECTOR_DISTANCE('cosine', …)` on rows whose `embeddingModel` equals the query's model, ordered by distance, `distance ≤ SEMANTIC_MAX_DISTANCE` = 0.35); `rank.ts` merges: keyword hits first in v0.2.0's order, then semantic hits not already present by id, still within the §4 tiers (library before cache before sources). A simpleMode session's semantic pass runs on `verified = true` own-library rows only and skips the cache, as the keyword pass does. `embed` returning null (no key, cap, error, AI off) leaves v0.2.0's behaviour exactly; the lookup test with a null `embed` is v0.2.0's test unchanged.
- **The library search** (`GET foods?q=&mode=semantic`): the same semantic merge over the space's rows when `mode=semantic`, which `Bibliotek-Telefon`'s "Søg i mad" and `Bibliotek-Desktop`'s "Søg i biblioteket" send on Enter (v0.2.0's `SearchField.onSubmit`); as-you-type stays keyword. The simpleMode "Find noget andet" search (§8) submits with `remote: true` on Enter too, so a child's spelling reaches the semantic pass over the verified list (§5.1 "a child's spelling doesn't matter").

## 9. Test strategy (extends v0.1.0 §8, v0.2.0 §8 and v0.3.0 §9)

- Unit tests with vitest next to the code; every acceptance criterion has one; `pnpm -r test` needs no network, database, browser, Azure or model. **No unit test calls a provider**: adapters take `fetch` (voyage, azure-openai, ollama) or an SDK client with a stubbed transport (anthropic) and are tested against `fixtures/ai/<adapter>/*`; every service, route, timer and screen is tested with `FakeAiProvider`, whose scripted answers are the same Zod shapes. A lint boundary fails if `@anthropic-ai/sdk` or a provider host appears outside its adapter folder, and `FakeAiProvider` outside tests, the seed, the CLI, the registry and `evals/`.
- **The evals are the only place a real provider is called**, and only with `ANTHROPIC_API_KEY` present: `pnpm --filter ./evals test` always runs the harness against `FakeAiProvider` with the recorded fixtures (so the scorer, the schemas and the dosing check are exercised in every run) and runs the live set only when the key is set, printing "live evals skipped: no ANTHROPIC_API_KEY" otherwise and exiting 0. The live set, per role: the parse cases (≈ 30 tool loops of 2–4 Sonnet 5.5 completions, ≈ 90 calls), the meal-insight cases (≈ 10 Sonnet calls), the normalisation cases (≈ 10 Haiku 5.5 calls), the week-insight cases (≈ 5 Fable 5.1 calls) and the photo cases present (Sonnet vision, 0..N). **In PR CI** (`ci.yml`, on prompt or eval changes) the harness runs the parse set, the normalisation set, the meal-insight set and at most 10 photo cases; **at release** (`release.yml`) everything. Concurrency 4 with `retry-after` on 429 (never a red build from a rate limit), a hard run budget of 3 minutes and 200 calls that fails the run when exceeded, and the capped wrapper counting every call. The live set fails the build when a score drops below `evals/thresholds.json`; the thresholds are set by the lane from its first live baseline minus a margin for the models' non-determinism (these models take no `temperature`), then fixed in the file and changed only by a reviewed PR: parse item recall, portion-within-±25 %, photo carbs within ±30 % (enforced only when at least 20 photo cases have an image), zero dosing hits on any output string, zero occurrences of "trykket"/"registreringen" in insight text (decision 9). Cost per full live run ≈ $2 (≈ 100 Sonnet calls ≈ $1, 5 Fable calls ≈ $0.7, Haiku and Voyage negligible).

## 12. Decisions taken by the planner

Each is a choice the spec or the design left open, with the reason. The owner can veto any of them by opening a `needs-owner` issue; decisions 2, 9 and 22 are also listed in task 11 so the owner sees them.

1. **Model roles, not ids, at every call site.** `small` → `claude-haiku-5-5` (OFF name normalisation: the spec's "small model, cached forever"), `everyday` → `claude-sonnet-5-5` (parse, vision, the meal sentence), `insight` → `claude-fable-5-1` (the weekly summary), as the spec names them; the ids live in the `anthropic` adapter only, so a model change is one line. Verified against the `claude-api` skill on 2026-10-15: these models reject `budget_tokens`, assistant prefill and forced `tool_choice`; the adapter sends none of them and uses `output_config.format` for every structured output.
2. **Embeddings are `vector(1024)` and the `anthropic` adapter embeds through Voyage AI (`voyage-3.5`, 1024 dimensions).** Anthropic has no embeddings endpoint and its documentation points to Voyage; 1024 is a dimension all three adapters can produce (`text-embedding-3-small` with `dimensions: 1024`; Ollama's `mxbai-embed-large`), so one column serves every provider and `Food.embeddingModel` records which one filled it. A second vendor and key is the price; it is optional, and without it search is v0.2.0's keyword search. Azure SQL's `vector` type and `VECTOR_DISTANCE` are GA (June 2025) and need the SQL Server 2025 container and compatibility level 170 for the integration tests.
3. **Enrichment (normalisation, then embeddings) runs in one poller timer every 15 minutes**, not on the write path: the meal-save path stays fast and key-free, `addCandidate` keeps its signature for the other lanes, a provider switch re-embeds everything by itself, and a renamed food is found by keyword in the meantime. `setEmbeddings` writes two bookkeeping columns and does not emit, as v0.1.0's `sourceFailures`/`lastSeq` do not; a space row whose *name* changes emits `food.updated`. Each space's rows go through that space's provider; the shared cache through `AI_CACHE_EMBED_PROVIDER`; a space with AI off is skipped entirely.
4. **Semantic search runs on submit only** (`remote: true`, three characters or more), with keyword hits first and a cosine-distance cut-off of 0.35, inside the spec's tiers (own library above cache above sources). Per-keystroke embedding would cost a call per letter; the §4 order is the product's promise and is kept. The simpleMode search submits on Enter so a child's spelling reaches the semantic pass over the verified list.
5. **Two caps, one call path, one guard.** `AI_DAILY_CAP` (50) counts `complete` and `vision`; `AI_EMBED_DAILY_CAP` (500) counts `embed`, because a search embedding costs a thousandth of a vision call and 50 searches a day is too few for a family. Both are per space per local day, enforced in `CappedAiProvider` before the provider is called; the same wrapper validates every output and runs the dosing guard over every string it returns, so no call site can forget either. `aiForSpace` is the only constructor in `web/`; the poller and the evals construct the same wrapper. `AiCall` rows are bookkeeping with no content and do not emit (decision 3's reasoning). The deployment-wide cache enrichment has its own cap (2000).
6. **Structured outputs are the Zod contracts** (`output_config.format` on Anthropic, `json_schema` on Azure OpenAI, `format` on Ollama); the schemas have no field that could hold an amount, a unit or a ratio (type test), so the spec's "the output schema has no such field" is a compile-time fact.
7. **Effort `low` for everyday calls and `medium` for both insights**, no `thinking` parameter, non-streaming, `max_tokens` 4096, per-role timeouts (20/30/120/10 s): every output here is a few lines, and the weekly runs in the poller where a two-minute call is harmless.
8. **A refusal is a soft failure, no server-side fallback.** `stop_reason: "refusal"` becomes `ai-unavailable`; the product uses exactly the models the spec names and never routes a plate photo to another model silently.
9. **The narration never uses the word "bolus".** The dosing-vocabulary list (v0.1.0 §8) contains it, generated text cannot be allow-listed, and the spec's test must fail on dosing vocabulary in insight text; so the carer's timing tap reaches the model as `leadMinutes` in a re-shaped `InsightStats` (no `bolus*` key anywhere in the input), and the prompts name the Danish noun **"forspringet før måltidet"** (the lead before the meal), which maps one-to-one to the drawn tile "12 min · før måltidet". The desktop artboard's sentence ("De gange bolus er givet 10–15 minutter før…") is therefore not reproducible verbatim; the model will say "De gange forspringet før måltidet var 10–15 minutter, blev toppen under 10." Recorded as a design deviation and listed in task 11 for the owner. "Trykket" and "registreringen" are refused as alternatives (ambiguous with logging the meal; an eval checks). A guard hit is retried once with a stricter instruction and then rejected; a failed question is dropped and counted, the rest kept.
10. **The raw-readings boundary is structural**: `InsightStats`/`InsightNumbers` are built from `MealStats`/`WeekNumbers` values by `input.ts`, the AI folders cannot import `Reading`, the history repository, `week-input.ts` or `web/src/lib/history/` (lint boundary), routes and the poller do the computing and hand over the re-shaped statistics, and the serialised input is tested to contain no series. The peak value is a statistic, as the design's own notice says.
11. **The meal sentence is generated on demand and cached by `statsHash`; the weekly summary is generated by the poller.** The meal sentence appears when the three-hour window is complete (before that the numbers would change under it) and Sonnet 5.5 answers within a web request. The weekly uses Fable 5.1, which can think for a minute or more — longer than a Static Web Apps request allows — so an hourly poller timer generates it between Sunday 18:00 and Monday 06:00 local (so "klar søndag aften" is true) and `insight.created` delivers it live; the web route only reads the cache. `shared/src/insights/` (store and week-input over `WeekSource`) exists so the poller and the web share one writer and v0.3.0's pure `stats/` functions, without the poller importing `web/`.
12. **The weekly summary is `{ summary, questions }`; desktop renders the questions only, as drawn.** The artboard deliberately keeps the week's numbers as tiles ("Tallene er regnet direkte på målingerne…") and the AI card as questions; a prose paragraph beside "ikke et råd" would read like a verdict. The summary is kept in the contract (spec §5.4 names it) and shown on the undrawn phone week view's "Ugens opsummering" card above the questions. Questions are editable ("Ret spørgsmålene", `questionsEdited`) and copyable; the edit emits `insight.updated`.
13. **Prompts live beside their service** under `shared/src/ai/<use>/prompt*.ts`, where `ci.yml`'s existing filter (`evals/`, `web/src/ai/`, `shared/src/ai/`) triggers the evals on a change and the prompt-file dosing test finds them (and asserts it found them all).
14. **The `lookup` tool runs with the session's rights and `remote: true`**, at most eight calls per parse: the model never sees more than the family's lookup results, a simpleMode session cannot reach parse at all, and OFF's rate limit is the adapter's concern (a `rate-limited` status is a tool result, not an error).
15. **Voice fills the field; "Find maden" sends.** One extra tap makes the explicit-action boundary unambiguous and testable, and lets the person correct the transcript. The browser's speech recognition is a third-party service outside Frejsi (Chrome sends audio to Google; Firefox has none); the Settings notice says so in one sentence, so the rule "sent only when someone taps" is honest about what the mic tap sends and to whom.
16. **The shutter is the explicit action for photos**, in `ask` and in the Say sheet; v0.2.0's meal photo attach never reaches AI. `Log-Simpel`'s drawn dashed tile "Noget andet? / Tag et billede" is restored and v0.2.0's search over the verified list becomes the link "Find noget andet" under it, so a child never sees "Noget andet?" twice with different outcomes.
17. **"Spørg en voksen" creates an unverified `ai` food with the photo and asks; it does not log a meal.** The Bibliotek artboards draw exactly this row ("Alma spurgte 14:52 · AI fra billede · Et gæt"), the carer's correction is v0.2.0's edit-and-verify, and a child's guess never becomes a carb total on the curve. The drawn "ca. 20 g" per 100 g is derived from the items' grams when they are all known.
18. **OFF names are normalised by the enrichment timer**, once per `sourceRef`, within a quarter hour of the first pick or cache write, with the original kept in `Food.sourceName`; a failure keeps the original name and is not retried; `origin: ai` and typed rows are never normalised. A family sees the raw name briefly; the spec's "normalised once at import … cached forever" holds for every later lookup.
19. **The evals always run their fake set and run live only with a key, capped and budgeted.** A missing key must not silently skip the schemas and the dosing check; the live adapter runs inside `CappedAiProvider` with a 200-call cap and a 3-minute budget, at concurrency 4 with `retry-after`, so neither a harness bug nor a rate limit can burn the key or redden a build; PR CI runs the text sets and a 10-photo smoke subset, release everything; thresholds are fixed numbers set from the first live baseline minus a margin. About $2 per full live run.
20. **AI is opt-in per space** (`aiEnabled` default false, owner only), provider keys are deploy-wide, and an unconfigured provider cannot be chosen. A fork without keys ships v0.3.0 behaviour with the AI section saying so.
