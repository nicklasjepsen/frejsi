## 1. What v0.5.0 is

When `v0.5.0` is tagged and `release.yml` is green, Frejsi is something another family, in another country, can run and contribute to:

- **Three glucose sources behind one interface** (§3). Settings → Glukosekilde shows the three cards the design draws: Dexcom Share (v0.1.0), **Nightscout** (a URL plus an access token or API secret, probed and stored in Key Vault like the Dexcom login, polled by the same five-minute cycle, readings `source: "nightscout"`) and **Manuelt** (no device: owners and carers type finger-prick readings on Now, phone and desktop, each with its time, stored and emitted exactly like a sensor reading, `source: "manual"`, never without its age, never to a viewer). One source at a time per space, as drawn.
- **"Send rettelsen til Open Food Facts"** (§4). When a carer edits a food that came from Open Food Facts and ticks the drawn checkbox before saving, Frejsi sends the corrected carbohydrates per 100 g and the serving size to OFF's write API under app name "Frejsi", with the deployment's OFF account from Key Vault. Unticked by default, never remembered, never automatic; absent when the deployment has no OFF account. The write API sits behind a `FoodContributor` interface beside `FoodSource`, with recorded fixtures, so a `usda` plugin can contribute to its own source the same way.
- **The poller authenticates to Azure SQL with its managed identity.** The Function App gets a user-assigned identity whose client id is known to Bicep, so `deploy.sh` can create its contained database user by SID (no Microsoft Graph lookup, which the deploy principal cannot do); the Function App gets the server and database names instead of the `DATABASE_URL` Key Vault reference; `@frejsi/shared`'s Prisma client uses `@prisma/adapter-mssql` with Entra authentication when no `DATABASE_URL` is present. The web app keeps SQL authentication, because Static Web Apps gives hybrid Next.js no identity (v0.1.0 decisions 10 and 11); the password stays in Key Vault for it and for migrations, with least privilege. The cutover is one release and is documented with its rollback.
- **A deployment's country is configuration**: `DEFAULT_LOCALE`, `FOOD_SOURCES` and `OFF_COUNTRY` travel from repository variables through `deploy.sh` into the app, so a fork in Norway sets three variables and edits no code; the i18n lint that keeps Danish out of `web/src` is extended to `shared/src` and `poller/src`.
- **"Deploy your own" in fifteen minutes of your own steps** (§9): `docs/deploy-your-own.md`, written for a fork, from the Azure prerequisites and the OIDC app registration through the repository variables and secrets, the first release (a `workflow_dispatch` with the infra box ticked, because a fork inherits tags and no milestones), the custom domain *before* the first owner's bootstrap (passkeys bind to the hostname), the costs, and what to expect from the alert. `.env.example` is complete and proven so by a test; `README.md` stops saying "no code yet"; `docs/architecture.md` explains the three plugin interfaces (`GlucoseSource`, `FoodSource` with `FoodContributor`, `AiProvider`) and how to add a food or glucose source for another country; `CONTRIBUTING.md` says how a plugin PR is built, signed off and reviewed.
- **Docker Compose for non-Azure users** (§9), as the second deploy path, starting only after the first has worked (a green `release.yml`): SQL Server, Azurite, a migration step, the web app, the poller and a file-backed `Secrets` adapter, with the fake source or a real one, documented in `docs/deploy-your-own.md`. The planner's reasoning for including it is in §8.
- **Release**: a second fictional space without a sensor in the seed, Playwright for the manual entry, the source cards and the OFF question (against a fake contributor), Prisma integration tests for the manual upsert, and the runbook.

## 4. Zod contracts

All additions are `.strict()` where the v0.1.0 schema they extend is; the dosing-vocabulary test keeps walking every schema key through `shared/src/schemas/index.ts`, and the viewer forbidden-keys walk of v0.3.0 §9 covers the new event payload.

- `GlucoseSourceType = dexcom-share | nightscout | manual`; `PolledSourceType = Exclude<GlucoseSourceType, "manual">` is the type `source-connect`'s `ADAPTERS` and the poller's factory are keyed by, so a new polled type without an adapter is still a compile error and `manual` needs none. `GlucoseSourceConfig` (discriminated on `type`): `{ type: "dexcom-share", region, secretRef }` (unchanged), `{ type: "nightscout", secretRef }`, `{ type: "manual" }`. The Nightscout URL is part of the credential in Key Vault, not of the config: the database stores `{ type, secretRef }` and nothing that locates or opens a person's Nightscout site (decision 2). `secretRef` is `glucose-<spaceId>` for both polled types; a switch overwrites the one secret (decision 3).
- `NightscoutCredential = { url: https URL (no query, no fragment, no credentials in the authority), token?: string (1–200), apiSecret?: string (1–200) }` with the refine "exactly one of `token`, `apiSecret`"; `serializeNightscoutCredential` / `parseNightscoutCredential` as the Dexcom pair (`shared/src/glucose/nightscout/credential.ts`). `http://` is rejected (decision 4).
- `ConnectSourceRequest` becomes a discriminated union on `type`: `{ type: "dexcom-share", spaceId, region, username, password }` (today's shape), `{ type: "nightscout", spaceId, url, token?, apiSecret? }` (the same one-of refine), `{ type: "manual", spaceId }`. `ConnectSourceResult` is unchanged (`ok` with `secretRef`, `bad-credentials`, `unreachable`); the `manual` variant never reaches `source-connect` (§5).
- `ManualReadingRequest = { ts?: ISO datetime (default now), value: number, unit: GlucoseUnit }`. The route converts to mmol with one decimal through `mgdlToMmol` when `unit` is `mgdl`, then validates against `Reading` (0–40 mmol); `ts` must lie within the last 24 hours and at most 5 minutes in the future (`reading-out-of-window`). The response is the stored `Reading`.
- `PollOutcomeCode` (`shared/src/glucose/poll-cycle.ts`) gains `manual`: the cycle saw a manual space and did nothing.
- `FoodContributor` (`shared/src/food/types.ts`): `{ id: string; contribute(correction: FoodCorrection, signal: AbortSignal): Promise<ContributionResult> }`. `FoodCorrection = { barcode: string (8|12|13 digits, valid checksum), carbsPer100g?: number (0–100, one decimal), servingSize?: { grams: number (1–5000), label?: string (1–40) }, appRef: string (1–64) }` — the pseudonymous `app_uuid` (decision 11); no name, no photo, no person (decision 10). `ContributionResult = { status: "ok" | "bad-credentials" | "rejected" | "rate-limited" | "error" }`. `ContributionsView = { available: string[] }` (the plugin ids with a configured contributor, e.g. `["off"]`; a type test asserts the view has no credential, host or glucose key).
- Event appended to `EventType` and the `EventEnvelope` union: `food.contributed { foodId, source }` to `space-<id>` (every member; the payload has no glucose key, type test).
- `ApiError` codes with a `da` and an `en` message each, appended by task 1: `source-not-manual` (409: a finger-prick reading for a space whose source is a sensor), `reading-exists` (409: a sensor reading already holds that timestamp), `reading-out-of-window` (400), `source-url-invalid` (400: not an https URL), `contribution-unavailable` (503: no contributor configured for that origin), `contribution-rejected` (502: the source refused or the credentials failed). `simple-mode` (v0.2.0) is reused for the two writes a simpleMode session may not make here.

## 5. Glucose sources: `nightscout` and `manual` (spec §3)

**Nightscout adapter** (`shared/src/glucose/nightscout/`), the Nightscout REST API v1, `fetch` injected like `OffSource`, a 30 s deadline per call like Dexcom:

- `fetchSince(since)`: `GET {url}/api/v1/entries/sgv.json?find[date][$gte]={since in ms}&count={n}` with `n` = 6 for a 30-minute window and 288 for the first run (the cycle's two windows, v0.1.0 §3; the adapter derives `n` from `since` as `ceil(minutes / 5)`, capped at 288). Entries carry `sgv` (always mg/dL in Nightscout's API regardless of the site's display unit), `date` (ms since epoch) and `direction`. Mapping: `mmol = mgdlToMmol(sgv)` (one decimal, the one conversion of v0.1.0 decision 13); `direction` `DoubleUp` → `double-up`, `SingleUp` → `single-up`, `FortyFiveUp` → `forty-five-up`, `Flat` → `flat`, `FortyFiveDown` → `forty-five-down`, `SingleDown` → `single-down`, `DoubleDown` → `double-down`, `RATE OUT OF RANGE` → `rate-out-of-range`, `NONE`, `NOT COMPUTABLE` or absent → `not-computable`; entries without `sgv` or `date`, and `type` other than `sgv`, are dropped; the result is oldest first, de-duplicated on `date`, newer than `since`.
- **Authentication**: the `api-secret` request header carries the SHA-1 hex digest of `apiSecret` (Nightscout's `API_SECRET` convention) or the access `token` as given (Nightscout's subject tokens are accepted in that header); the token is never put in the URL, so no log, telemetry or proxy sees it (decision 5). Exactly the two forms the credential schema allows.
- `probe()`: `GET {url}/api/v1/verifyauth` with the same header → `ok` when the body's `message` is `"OK"` (older sites) or an object with `canRead: true` (newer sites), `bad-credentials` on `UNAUTHORIZED`, `canRead: false` or HTTP 401/403, `unreachable` on a network error, a timeout, a non-JSON body or a redirect (redirects are not followed: a site that answers 3xx is misconfigured, and following one could leak the header to another host). A site whose default role already allows reading answers `ok` for any credential; "ok" therefore means "readable with this credential or without one", which the adapter README says.
- Errors carry the HTTP status or the Nightscout message word, never the URL or a body; the log lines are `spaceId`, `code`, `ms`. There is no credential-retry back-off (Nightscout does not lock accounts); a 401 every cycle takes the space to `disconnected` after three like any failure.

**The poller** (`poller/src/`): `createSourceFactory({ secrets, env })` returns `FakeGlucoseSource` for every space when `env.FAKE_GLUCOSE_SOURCE === "1"` (today only the CLI honours the variable; the timer must too, so Docker Compose and a laptop without credentials show a curve) and otherwise reads the secret by `config.secretRef` and dispatches on `config.type` — `dexcom-share` → `DexcomShareSource` (the existing cache-per-space and change-detection, unchanged), `nightscout` → `NightscoutSource` with the parsed `NightscoutCredential`; a secret that does not parse as the credential the type expects is `secret-invalid` as today (the one secret name is overwritten on a switch, decision 3). `poll.ts` and `cli.ts` wire it, so `pnpm --filter ./poller poll --once --space <id>` polls a Nightscout space too. `runPollCycle` parses each space's config first and, for `type: "manual"`, records outcome `manual`, touches neither `sourceFailures` nor `sourceStatus`, calls no factory and emits nothing: a manual space is never polled and can never become `disconnected`. `source-connect`'s `ADAPTERS` becomes `Record<PolledSourceType, …>` and gains `nightscout`; on `ok` it serialises the type's credential into `glucose-<spaceId>`. A `manual` request to `source-connect` is 400 `validation`: the Settings route handles `manual` itself.

**Manual readings** (`web/`): `POST /api/spaces/[spaceId]/readings` as owner or carer (viewer 403, non-member 404; a simpleMode session 400 `simple-mode`, decision 7), body `ManualReadingRequest`. `addManualReading` (`web/src/lib/readings/`, the only `prisma.reading` writer in `web/`): requires the space's `glucoseSource.type` to be `manual` (409 `source-not-manual`, so hand-typed values never mix into a sensor stream; the stream stays "raw, never edited"); upserts `(spaceId, ts)` with `mmol`, `trend: "not-computable"`, `source: "manual"`, refusing with 409 `reading-exists` when the existing row's `source` is not `manual` (a leftover sensor reading from before a switch); moves `lastReadingAt` forward only (the cycle's conditional-write rule); emits `reading` through `emit` (to `space-<id>-glucose`, so a viewer's token never carries it, and `events?since` strips it for a viewer as it strips every `reading`); tracks the `reading.stored` custom event so the 35-minute alert measures the whole chain for a manual deployment too (decision 8). Re-entering a value at the same timestamp replaces it: that is how a typo is corrected (decision 6). `useLiveFeed` keys its `readings` state by `ts`, so the re-emitted reading replaces the old one on every open screen (additive; v0.1.0's hook tests stay green).

**On the screens**: a space whose source is `manual` gets a "Indtast måling" button (plan-added copy; no artboard draws the manual entry, design gap) on Now — on the phone a `SecondaryButton` under the hero where the status pill sits, on desktop a `SecondaryButton` in the glucose card's status line — opening `ManualReadingSheet`: a `NumberInput` in the space's unit (decimal comma in `da`, whole numbers for mg/dL), the time (a "Nu" chip pressed by default and a time field limited to the last 24 hours), the `PrimaryButton` "Gem måling", and the errors "Tallet ser ikke rigtigt ud – tjek enheden" and "Tidspunktet skal være inden for det sidste døgn". The simpleMode Now has no entry point (decision 7). The hero then shows the new value exactly as a sensor reading: number, no arrow and no trend word for `not-computable` (v0.1.0 design gap 4), and the age line. The sparkline and the day curve draw a reading with no neighbour within `COVERAGE_CAP_MINUTES` (15, v0.3.0 §5) as a dot and join nothing to it, so a manual space's chart is points, not a line between finger-pricks hours apart. The status copy for `manual` omits the "forbundet" word, which describes a connection nobody makes: the phone row reads "Manuelt · sidste måling 15:13", the desktop card "Fingerprik-målinger · sidste måling i dag 15:13" (as drawn: "Fingerprik-målinger tastes ind. ## 7. Managed identity for the poller's database connection (spec §1 "managed identity for all secrets", v0.1.0 decision 11)

- **Why a user-assigned identity.** Azure SQL resolves `CREATE USER … FROM EXTERNAL PROVIDER` through Microsoft Graph with the *server's* identity, and the server has none; giving it one and the Directory Readers role is a tenant-level step no pipeline can do and no fork should have to. The alternative is `CREATE USER [name] WITH SID = <application id as varbinary(16)>, TYPE = E`, which needs no Graph but needs the identity's *client (application) id*, which ARM exposes only for a user-assigned identity. So `functionapp.bicep` creates `id-<baseName>-<suffix>` (`Microsoft.ManagedIdentity/userAssignedIdentities`), assigns it to the Function App (`identity: { type: 'UserAssigned' }`), sets `keyVaultReferenceIdentity` to it and the app setting `AZURE_CLIENT_ID` to its client id (so `DefaultAzureCredential` in the poller — Key Vault, Web PubSub and now SQL — uses it without code changes); `roles.bicep` assigns Key Vault Secrets Officer and Web PubSub Service Owner to its principal; `main.bicep` outputs the client id (decision 22). The Function App's settings carry `SQL_SERVER_FQDN` and `SQL_DATABASE` (from the `sql` module's outputs) and no longer the `DATABASE_URL` Key Vault reference. `sql.bicep` is unchanged: the server keeps the deploy principal as Entra admin and SQL authentication stays on, because the web app needs it (below).
- **`deploy.sh`**, in this order: between `prisma migrate deploy` and the firewall-rule delete (the runner's rule is still open), as the Entra admin (`sqlcmd --authentication-method ActiveDirectoryDefault`, SQL from a mode-600 file), runs idempotently `IF NOT EXISTS (SELECT 1 FROM sys.database_principals WHERE name = N'<identity name>') CREATE USER [<identity name>] WITH SID = CONVERT(varbinary(16), CAST('<client id>' AS uniqueidentifier)), TYPE = E; ALTER ROLE db_datareader ADD MEMBER …; ALTER ROLE db_datawriter ADD MEMBER …;` with the client id read by `az identity show` (an assignment, checked non-empty) — the poller reads and writes rows and never runs DDL. After the poller's zip is deployed and `WEBSITE_RUN_FROM_PACKAGE` is verified (so the new bundle, which understands `SQL_SERVER_FQDN`, is the one running), it deletes the Function App's `DATABASE_URL` setting (`az functionapp config appsettings delete`, a no-op when the setting is absent, as on a fresh fork), because `functionapp/appsettings.bicep`'s `union()` keeps every live setting a Bicep deploy no longer names: an infra deploy between the Bicep change and the first `deploy.sh` run still carries `DATABASE_URL`, which is why the delete lives in `deploy.sh`, every release, idempotent. The application SQL login (`frejsi_app`) stays for the web app and for `prisma migrate deploy`; a new deployment creates it with `db_datareader`, `db_datawriter` and `db_ddladmin` instead of `db_owner` (an existing login is left as it is; the README says how to tighten it by hand); v0.4.0 #65's compatibility-level step is `ALTER DATABASE` and must run through `sqlcmd` as the Entra admin, not as that login — the lane checks what #65 landed and moves it if needed. The script also writes `OFF_CONTRIBUTE_USER`/`OFF_CONTRIBUTE_PASSWORD` to the SWA settings only when the Key Vault secrets `off-contribute-user`/`off-contribute-password` exist (the v0.4.0 #65 pattern, same skip notice), and `DEFAULT_LOCALE`, `FOOD_SOURCES` and `OFF_COUNTRY` from the environment variables of the same names when set (`release.yml` passes `vars.DEFAULT_LOCALE`, `vars.FOOD_SOURCES`, `vars.OFF_COUNTRY`; today nothing carries `FOOD_SOURCES` or `OFF_COUNTRY` to production, so a fork could not change them and production may have no plugins switched on unless #35/#41 did it — the walkthrough tells every installation to set them). `release.yml` and `preview.yml` read the resource group as `vars.AZURE_RESOURCE_GROUP || 'frejsi'`, so a fork may name its group.
- **Prisma** (`shared/src/db/`): `createPrismaFromEnv(env)` returns today's `PrismaClient` when `DATABASE_URL` is set (web, local dev, tests, Docker) and, when it is absent and `SQL_SERVER_FQDN` and `SQL_DATABASE` are set, a `PrismaClient` over `@prisma/adapter-mssql` (the package matching the pinned Prisma 6.19.3, and the `driverAdapters` preview flag only if that version still needs it) with the `mssql` config `{ server, database, authentication: { type: "azure-active-directory-default", options: { clientId } }, options: { encrypt: true, trustServerCertificate: false } }` (tedious acquires and refreshes the token through `@azure/identity`'s `DefaultAzureCredential`, which on Functions is the identity `AZURE_CLIENT_ID` names). With neither set the factory throws an error naming both options — but the exported `prisma` singleton stays non-throwing at import (constructed lazily on first use), because `shared/src/index.ts` exports it eagerly, `web`'s unit tests set no `DATABASE_URL` and `next build` imports every route module. `poller/src/functions/poll.ts`'s `const db: PollDb = prisma` is untouched; the esbuild bundle gains `mssql`/`tedious` and their dependencies (pure JavaScript; the lane proves `pnpm --filter ./poller build` still produces a self-contained `dist/` and adjusts `poller/esbuild.config.mjs`'s externals if something must stay out).
- **What does not change, and why**: the web app on Static Web Apps has no usable managed identity (v0.1.0 decision 10), so it keeps `DATABASE_URL` from Key Vault via `deploy.sh`; migrations run in the pipeline through that URL too. Entra-only authentication on the server therefore stays off. The gain is that the poller — the component that runs unattended every five minutes with a real identity — holds no database password, and that the password's privileges shrink. `infra/README.md` says this in those words.
- **Cutover** (one release, documented in `infra/README.md` by task 2): the infra job runs because `infra/` changed (the owner's tap) and deploys the identity, the roles and the new settings; the running bundle keeps working on `DATABASE_URL` (still live through `union()`) while the identity's Key Vault role propagates (a minute); the deploy job creates the contained user, ships the new bundle, then removes `DATABASE_URL`; the next poll cycle connects with the identity. Rollback is the redeploy of the previous tag through `workflow_dispatch`: the infra job runs by itself because the `infra/` diff between the two tags is non-empty (the infra box is for variable-only changes), Bicep restores the Key Vault reference and the old bundle reads it. The README names the one symptom to look for (`Login failed for user '<token-identified principal>'` in the poller's log means the contained user is missing; the idempotent script in every release is also the repair: rerun the deploy job) and that the identity's display name is `id-<baseName>-<suffix>` in Azure and the contained user's name in SQL.

## 12. Decisions taken by the planner

Each is a choice the spec or the design left open, with the reason. The owner can veto any of them by opening a `needs-owner` issue; decisions 8, 9 and 14 are also listed in task 10 so the owner sees them.

1. **No migration in v0.5.0.** `Reading.source` and the JSON `Space.glucoseSource` already carry everything the three sources need; contributions are events (decision 12). Lanes never queue behind a schema.
2. **The Nightscout URL lives in the Key Vault credential, not in the database.** The spec stores `{ type, region, secretRef }` for Dexcom; a Nightscout URL is a person's whole glucose history behind one secret, and the database should not say where it is. The status screens therefore show "Nightscout" and never the hostname.
3. **One secret name per space, `glucose-<spaceId>`, for both polled types**, overwritten on a switch; the poller parses it by `config.type`. A second name would leave orphaned credentials in Key Vault, which the web app cannot delete (no identity).
4. **Nightscout over https only.** The token travels in a header; a plain-http site would send it in clear. A home-network site on http is not reachable from Azure anyway; Docker Compose users with a local Nightscout can put it behind a TLS proxy.
5. **The token goes in the `api-secret` header, never in the URL**, although Nightscout accepts `?token=`: URLs reach proxies, telemetry and sometimes logs; headers reach none of ours (the logger has an allow-list of keys). The API-secret form is the SHA-1 hex digest, Nightscout's own convention.
6. **A finger-prick typo is corrected by re-entering the value at the same timestamp**, which replaces the row and re-emits the reading; there is no delete route and no `reading.deleted` event. The stream stays "raw, never edited" in the sense that matters (no editing of sensor data), and the hook's replace-by-`ts` is the only client change.
7. **A simpleMode session cannot enter a finger-prick reading**, and the simpleMode Now has no entry point. A mistyped glucose value is worse than a mistyped portion (v0.2.0 decision 11's reasoning), and a child without a sensor has adults who measure. Vetoable: it is one route check and one button.
8. **The 35-minute alert is unchanged, and the manual route tracks `reading.stored` too.** The alert measures "a reading reached the database" (v0.1.0 decision 21); on a deployment whose only source is manual it fires whenever nobody has measured for 35 minutes, which is true and is said in the docs. A parameter to disable it is a one-line follow-up the owner can ask for.
9. **The OFF write goes to `world.openfoodfacts.org` by default**, with the staging host as configuration and the docs' recommendation for a first try; the adapter adds the staging host's basic authentication itself, because that is OFF's fixed convention and not a secret. OFF's write API wants a logged-in account; Frejsi uses one account per deployment (the owner's or a dedicated one), identified by `app_name=Frejsi`, `app_version` and an `app_uuid` per space (decision 11), so OFF can attribute and, if needed, revert. `nutrition_data_per=100g` is sent so the value lands per 100 g whatever the product's basis was.
10. **Only carbohydrates per 100 g and the serving size are sent, never the name.** Families rename products for themselves ("Rugbrød, Schulstad Det Gode" is already v0.4.0's normalisation, not the label); OFF's product name is the label's. The drawn checkbox says "rettelsen" and the docs say which fields that means.
11. **`app_uuid` is the first 32 hex characters of `sha256(spaceId)`**: stable per space so repeated corrections from one family are one contributor to OFF, pseudonymous, and free of any person.
12. **Contributions are recorded as `food.contributed` events, not rows.** Nothing in the UI lists past contributions; the event is the audit trail and the live signal, and it keeps the milestone free of a migration.
13. **A deployment without an OFF account has no checkbox.** The feature is switched on by two Key Vault secrets (`foodContributors(env)`), like every plugin, and a fork never sees a control that cannot work.
14. **The poller moves to managed identity; the web app does not.** Static Web Apps gives hybrid Next.js no usable identity (v0.1.0 decision 10), so the web app keeps `DATABASE_URL`; the poller — unattended, every five minutes, with a real identity — stops holding a password, and the remaining login loses `db_owner`. The spec's "managed identity for all secrets" is met where the platform allows it, and the limit is written in `infra/README.md`. `@prisma/adapter-mssql` with tedious's `azure-active-directory-default` is used because it acquires and refreshes the token itself; no token plumbing in our code.
15. **A second fictional space without a sensor in the seed** ("Arnes rum": Arne, Mette) rather than switching Alma's space in the e2e, so earlier milestones' Playwright specs keep their Dexcom readings and the viewer checks stay meaningful.
16. **Docker Compose is in, as the last build wave, gated on the first green release**, with `FileSecrets` and `BLOB_PUBLIC_ENDPOINT` as the only new code and no second code path (§8). The roadmap's "local Web PubSub substitute" is not built: without Web PubSub the existing `NoopEventSink` and the client's 30-second poll are the live transport, which is what the code already does in local dev and in the release e2e. The spec's order ("one deploy path must work before a second exists") is kept as a precondition on the lane, not by moving the work to another milestone.
17. **`DEFAULT_LOCALE`, `FOOD_SOURCES` and `OFF_COUNTRY` are repository variables** that `release.yml` hands to `deploy.sh` and `deploy.sh` writes as app settings; `da` is the documented fallback when `DEFAULT_LOCALE` is unset. The product is Danish-first (spec), a fork is not; the schema default on `User.locale` stays `da` and the code sets the locale explicitly, so no migration. The runtime half (middleware or root layout, registration) sits in task 2 beside the pipeline half, so one lane owns the variable from `vars.*` to the first screen.
18. **The i18n lint is extended to `shared/src` and `poller/src`** with six exclusions (tests, the Frida dataset, the fold table, the dosing word list, the AI prompts, fixtures), and a literals test refuses `Europe/Copenhagen` and the syntactic default forms of `"da"`/`"dk"` outside five named places that are configuration or a documented fallback.
