## 1. What v0.1.0 is

When `v0.1.0` is tagged and `release.yml` is green, `https://frejsi.jepsen.ninja` shows one person's live Dexcom glucose to the people around them, and nothing else yet:

- The owner bootstraps the first space, invites people with a link or QR code, and everyone signs in with a passkey. Owners add devices and remove them. Roles are `owner`, `carer`, `viewer`.
- The poller reads Dexcom Share every five minutes, stores readings, and pushes each one to connected phones and desktops through Web PubSub, with the `events` table as source of truth.
- The Now screen (phone, desktop, simpleMode, dark, five accent colours) shows the value with its trend and its age, the three-hour sparkline (phone) or the day curve (desktop) with the target band, and the source status. A banner tells owners and carers when the source is down.
- Settings: connect Dexcom Share, glucose unit, target range, language, simpleMode per person, accent per person. People: members, roles, invites, devices.
- `/api/health` reports the deployed version. The PWA installs. `da` and `en` ship together.

Not in v0.1.0: foods, meals, history, AI, Nightscout, manual readings, photos. The tabs for them (Måltid, Mad, Historik) exist in the shell and open a calm placeholder page ("Kommer i en senere version"), so the navigation matches the design from the first release and nothing has to move later. On Now, the meal-related regions the artboards draw ("Sidste måltid", "Dagens måltider", the quick-link cards, "Min mad") are omitted, not drawn empty; in simpleMode only "Jeg spiser nu" is shown and opens the placeholder, and "Spørg en voksen" is absent until v0.4.0 confirms the flow. A viewer gets the viewer shell (I dag · Tidligere dage · Mere) with the notice "Blodsukker vises ikke her" and the placeholder for meals.

## 3. Prisma schema for v0.1.0

Spec §2 tables that v0.1.0 needs, plus what passkeys and the design require. `foods`, `meals`, `meal_items` are v0.2.0. Enums are `String` columns validated by the Zod enums in `shared/src/schemas/` (one source of truth, portable to Postgres in v0.5.0); JSON is `String @db.NVarChar(Max)` parsed with Zod (Prisma's SQL Server connector has no `Json`). Prisma's major is pinned in task 1 with `binaryTargets = ["native", "debian-openssl-3.0.x"]` for the Linux Consumption runtime.

## 4. Zod contracts (`shared/src/schemas/`)

- `Trend`: `double-up | single-up | forty-five-up | flat | forty-five-down | single-down | double-down | not-computable | rate-out-of-range` (Dexcom's set; adapters map to it).
- `Reading`: `{ ts: ISO datetime, mmol: number (0–40, one decimal), trend: Trend }`. There is no schema for a glucose value without `ts`.
- `GlucoseSourceConfig`: discriminated on `type`; v0.1.0 has `{ type: "dexcom-share", region: "eu" | "us", secretRef: string }`. `SourceStatus`: `not-configured | connected | disconnected`. `ConnectSourceRequest` (`{ spaceId, type, region, username, password }`) and `ConnectSourceResult` (`ok | bad-credentials | unreachable`) are the contract between the Settings route and the `source-connect` function.
- `Role`, `GlucoseUnit` (`mmol | mgdl`), `Accent` (`olive | plum | sea | forest | garnet`), `Locale` (`da | en`).
- Events: `EventType` and one payload schema per type; `EventEnvelope = { spaceId, seq, type, payload, ts }` as a discriminated union. v0.1.0 types: `reading` (`Reading`), `source.status` (`{ status, since }`), `space.updated` (`{ fields: string[] }`), `member.joined`, `member.updated`, `member.removed` (`{ userId, role? }`), `invite.created`, `invite.revoked` (`{ tokenHash, role, name, forUserId? }`), `device.added`, `device.removed` (`{ userId, passkeyId }`). `space.updated` is never used for a `User` column; user-level changes are `member.updated` to every space the user belongs to. Later milestones append `meal.*`, `food.*`.
- Auth: `SessionContext = { userId, name, simpleMode, accent, locale, memberships: [{ spaceId, role }] }`; `InviteView` (what the landing page gets: `name, spaceName, role, inviterName, daysLeft, forExistingUser`).
- Settings: `SpaceSettings` (name, glucoseUnit, targetLow, targetHigh, timezone, sourceType, sourceStatus, lastReadingAt), `UserSettings` (locale, simpleMode, accent).
- `Health = { ok: boolean, version: string, db: "ok" | "error", readings: "fresh" | "stale" | "none" }` — a coarse state, no timestamp and no value.
- `ApiError = { error: { code, message } }`; codes are stable strings, messages are translated client-side by code.

## 5. Events and live transport (spec §3b)

`emit(spaceId, type, payload)` lives in `shared/src/events/emit.ts` (task 1) and is the only way to write an event: it allocates `seq` with one atomic statement (`prisma.space.update({ data: { lastSeq: { increment: 1 } }, select: { lastSeq } })`), inserts `(spaceId, lastSeq)`, and after commit publishes the envelope to Web PubSub. Every API route and the poller call `emit` after their own write in the same request; a `Prisma` write to space data without a following `emit` is a guardian fail. The poller's bookkeeping columns `sourceFailures`, `lastReadingAt` and `lastSeq` are carried by the `reading` and `source.status` events and need no emit of their own.

Two groups per space, so that access is enforced by Web PubSub and not by the client (§3b) while the viewer never receives glucose:

- `space-<id>` — every event type except `reading`.
- `space-<id>-glucose` — `reading` only.

`/api/spaces/:id/negotiate` issues a client token with the groups baked into it (`groups: [...]`, auto-joined, no `joinLeaveGroup` role): `space-<id>` for every member, plus `space-<id>-glucose` only when the member's role is `owner` or `carer`. `/api/spaces/:id/events?since=<seq>` returns events after `seq` in order and strips `reading` for a `viewer`. `/api/spaces/:id/readings?hours=<1..24>` is 403 for a `viewer`.

`useLiveFeed(spaceId)` (web): negotiates, connects, fetches `events?since` on connect and on every reconnect, re-negotiates on reconnect (tokens expire), polls the same endpoint every 30 s while the socket is down or while `negotiate` answers 503 (no Web PubSub configured, as in local dev without `awps-tunnel` and in the release e2e), and exposes `{ lastSeq, readings, sourceStatus, connection }`. Screens read from the hook only.

The poller publishes through the Web PubSub REST API with its managed identity (`DefaultAzureCredential`, Web PubSub Service Owner); the web app, which has no usable managed identity on Static Web Apps (§7), uses the connection string placed in its app settings by `deploy.sh`. Free tier: 20 concurrent connections, 20k messages/day; 288 readings × ~8 devices ≈ 2.3k/day.

## 6. Auth and session (spec §2b)

- Registration: `POST /api/auth/register/options { inviteToken }` → `AuthChallenge` row + `@simplewebauthn/server` options (`residentKey: required`, `userVerification: preferred`, rpID derived from `APP_ORIGIN`, which is required; a request whose `Origin` differs is rejected). `POST /api/auth/register/verify` consumes the challenge, verifies, then in one transaction: creates the `User` (or, with `forUserId`, only the `Passkey` on the existing user), the `Membership` with the invite's role, marks the invite `usedAt`, creates the `Session`, emits `member.joined` (new user) or `device.added` (existing user).
- Login: `POST /api/auth/login/options` (discoverable credential, no username) and `/verify`: counter check, `lastUsedAt`, `lastSeen`, new `Session`.
- Cookie `frejsi_session`: value = session id, `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=7776000` (90 d). `getSession()` loads the row and user with memberships; `requireRole(spaceId, ...roles)` throws `403 forbidden` (`404 not-found` for non-members so space ids do not leak). `lastSeenAt` is touched at most once per hour.
- Revocation: deleting a passkey deletes its sessions and emits `device.removed`; removing a member deletes their sessions for that space's shell and emits `member.removed`; `POST /api/auth/logout`.
- Returning device: `/[locale]/welcome` offers "Log ind" (passkey sign-in with a discoverable credential) and, below it, the text that an invitation link is needed for a first visit; the middleware sends unauthenticated requests under `/[locale]/(app)` there. The invite page, `welcome` and `/api/health` are public.
- Bootstrap: `POST /api/bootstrap` with header `x-bootstrap-token` compared with `timingSafeEqual` against the `BOOTSTRAP_TOKEN` app setting and body `{ spaceName, ownerName, timezone }` creates the space and a single-use owner invite, emits `invite.created`, and returns the invite URL. Responds `404` once any `Space` exists. Never logs the URL or the token.

## 7. Configuration and secrets

Azure Static Web Apps gives hybrid Next.js no usable managed identity and no Key Vault references in app settings (the SWA identity serves only its built-in auth secrets, which Frejsi does not use). Secrets therefore reach the web app as app settings written by `infra/deploy.sh`, which reads them from Key Vault with the pipeline's OIDC identity. Nothing is ever in the repo or in a log; the hard rule holds. The Function App has a real managed identity and uses Key Vault references and `DefaultAzureCredential`. The one Key Vault write the product needs (the Dexcom credential) is done by the Function App's `source-connect` HTTP trigger, called by the Settings route.

## 8. Test strategy (spec §8)

- Unit tests with vitest next to the code (`*.test.ts`, `*.test.tsx` with `@testing-library/react` and jsdom). Every acceptance criterion below has one. `pnpm -r test` needs no `.env`, no database, no browser, no Azure: `shared`'s vitest config excludes `test/integration/**`, `web`'s excludes `e2e/**`.
- External APIs are never called in tests. Dexcom Share: hand-written JSON under `fixtures/dexcom-share/` in the documented shapes, with both the string (`"Flat"`, `"FortyFiveUp"`) and the numeric trend forms, fictional account ids and round numbers. Web PubSub and Key Vault: the `MemoryEventSink` and `MemorySecrets` fakes behind their interfaces. The poller is tested against `FakeGlucoseSource`.
- The dosing-vocabulary test (`shared/src/dosing.test.ts`, test name contains "dosing") scans `web/messages/*.json` and every Zod schema's keys, word-bounded and case-insensitive, for: `insulin`, `dosis`, `dose`, `dosing`, `ratio`, `correction`, `korrektion`, `ICR`, `ISF`, `IE`, `IU`, `bolus`, and the phrases `enheder insulin`, `insulin units`, `units of insulin`. The bare words `enhed`/`units` are not on the list because in this product they mean devices and the glucose unit. The allow-list is exactly: "regner aldrig insulin", "Frejsi · åben kildekode · regner aldrig insulin", "Frejsi er åben kildekode, regner aldrig insulin og erstatter ikke din sensor-app eller pumpe-app.", "never calculates insulin", "Frejsi · open source · never calculates insulin", "Bolus givet nu", "Bolus før måltid", "bolus given now", "bolus before meal", the pattern `Bolus HH:MM`, and nothing else. From v0.4.0 it also runs on generated insight text.
- Secrets: `gitleaks` runs in `ci.yml` with the repo's `.gitleaks.toml`; seconds.
- Prisma integration tests under `shared/test/integration/` against the SQL Server container, `pnpm --filter ./shared test:integration`, in `release.yml` only.
- Playwright under `web/e2e/`, `pnpm --filter ./web test:e2e`, in `release.yml` only: `playwright.config.ts` starts `next start` through `webServer` with `DATABASE_URL` from the job and `FAKE_GLUCOSE_SOURCE=1`, and `globalSetup` runs `prisma migrate deploy` plus the seed. Flows: the simpleMode Now screen (register through a virtual authenticator from an invite link, see number, arrow and age, the three-tab shell) at 360 and 1280 px; the viewer shell shows no glucose anywhere; installability (manifest) and the offline shell.
- Seed (`pnpm --filter ./shared seed`): the fictional space from the artboards (Alma's space, Jonas and Mette as owners, Birthe as carer with simpleMode off, Alma as carer with simpleMode on, Lærke as viewer), fake source. It creates memberships and invites through the same functions the routes use and fills readings by running one poll cycle with `FakeGlucoseSource`, so every row has its event; a test asserts the seeded `events` table has a gap-free `seq` and one `reading` per seeded reading. Refuses to run when `NODE_ENV=production`.

## 9. Error handling and observability (spec §7)

- API errors are `ApiError` with stable codes (`forbidden`, `not-found`, `invite-expired`, `invite-used`, `invite-revoked`, `last-owner`, `source-bad-credentials`, `source-unreachable`, `validation`), never stack traces; the client translates by code in `da` and `en`.
- Source status: three consecutive poller failures set `sourceStatus = disconnected` and emit `source.status`; a success sets `connected`. Owners and carers see the banner "Ingen forbindelse til {source} siden {time}" (`en`: "No connection to {source} since {time}") on Now and in Settings, where `{source}` is the `da.json`/`en.json` string keyed by `GlucoseSourceConfig.type` (`source.dexcom-share.name` = "Dexcom Share"), so a new source adds a string and no branch in UI code; polling continues (§3). The `SourceStatusBanner` component (props `{ status, since, sourceType }`) lives in the shell (task 3).
- Age: the client re-renders the age every 30 s from `ts`; after 15 minutes without a reading the status dot turns to the muted colour and the age keeps counting. There is no component path to a number without `ts`. Before the first reading, "Ingen målinger endnu".
- App Insights in web and poller through `shared/src/telemetry.ts`, whose initializer strips request bodies and any property named `name`, `email`, `username`, `password`, `mmol`, `photo`. The poller tracks a custom event `reading.stored` per new reading; the Bicep alert fires when none arrived for 35 minutes (sensor changes cause ~30 min gaps).
- `shared/src/log.ts`: structured JSON with an allow-list of keys (`spaceId`, `userId`, `count`, `code`, `ms`, `route`); any other key is dropped and a test proves a name does not reach the output.
- The poller wraps each space in its own try/catch; one failing space never stops the others.
- Web error boundaries render a kind page in the user's language with no technical detail.

## 12. Decisions taken by the planner

Each is a choice the spec or the design left open, with the reason. The owner can veto any of them by opening a `needs-owner` issue.

1. **v0.1.0 ships live glucose before food.** The foundation (auth, spaces, events, infra) is needed by everything and is the only part that needs the owner's hands; food lands on a running system in v0.2.0.
2. **Basic meal logging and the viewer's day move to v0.2.0**, meal-on-the-curve stays v0.3.0: "the child finds her lunchbox herself" needs a saved meal, not just a lookup.
3. **Two Web PubSub groups per space** (`space-<id>` and `space-<id>-glucose`), baked into the client token, so the viewer's token physically cannot join the glucose stream; the spec's single group would have pushed readings to viewers. Hyphens, not colons, in group names.
4. **Server-side sessions** (`Session` table, opaque cookie) instead of a signed JWT, so removing a device revokes it immediately.
5. **Challenges in a table** (`AuthChallenge`) instead of a signed cookie: no signing key to manage.
6. **Enums as strings + Zod, JSON as `NVarChar(Max)` + Zod, `credentialId` as a base64url string, `counter` as `Int`**: Prisma's SQL Server connector has no `Json`, cannot index `varbinary(max)`, and strings keep the schema portable to Postgres for v0.5.0.
7. **`seq` is allocated by an atomic increment of `Space.lastSeq`**, not by `max(seq)` under a lock: one statement, provable in the integration test, no raw SQL.
8. **Bootstrap through `POST /api/bootstrap`** guarded by a Key Vault-held token and dead once a space exists: a CLI or pipeline step would print the owner invite into a public Actions log.
9. **Dexcom credentials are entered in Settings** and written to Key Vault by the Function App's `source-connect` trigger (the SWA web app has no usable managed identity), not placed in Key Vault by hand: it matches the `Indstillinger` artboards ("Skift login"); the DB stores only the `secretRef`.
10. **Web app secrets are SWA app settings written by `deploy.sh` from Key Vault** with the pipeline's OIDC identity: Static Web Apps offers hybrid Next.js neither managed identity nor Key Vault references.
