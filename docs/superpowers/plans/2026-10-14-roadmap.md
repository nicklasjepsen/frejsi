# Frejsi — roadmap

**Status:** planned by the agents on 2026-10-14 under the owner's standing instruction (agents plan, review and start the first milestone without further sign-off; blockers go to `needs-owner` issues). Each milestone is a GitHub milestone and a release (`docs/agent-workflow.md` §1). The owner may re-cut any milestone that has not started.

Spec: `docs/superpowers/specs/2026-10-14-frejsi-design.md`. Design: `docs/design/`. Version numbers stay `v0.x.y` until the owner's family uses Frejsi daily; then `v1.0.0`.

The order follows the spec's priorities with one inversion: live glucose (priority 3) ships first, in v0.1.0, because it is the foundation everything else draws on (auth, spaces, events, infra) and because it is the only part that needs the owner's hands (Azure, DNS, Dexcom). Food (priority 1) follows in v0.2.0 on a running system.

## v0.1.0 — Foundation and live glucose

Plan: `docs/superpowers/plans/2026-10-14-v0.1.0-foundation.md`.

The monorepo (`web/`, `poller/`, `shared/`, `infra/`) with TypeScript strict, Zod contracts and the Prisma schema; Bicep for every Azure resource v0.1.0 needs in resource group `frejsi` (Blob Storage waits for photos in v0.2.0), the deploy script `release.yml` calls, OIDC login and the opt-in preview workflow; passkeys-only sign-in with invite links and QR codes, spaces with `owner`/`carer`/`viewer` roles, add-device links and device removal; the `dexcom-share` adapter behind `GlucoseSource`, the five-minute poller with idempotent upserts and the disconnected state; the `events` table as source of truth, `emit()` and Web PubSub push with the `useLiveFeed` hook; the Now screen on phone, desktop, simpleMode and dark, with the glucose value always carrying its age; Settings for the glucose source, units, language, simpleMode and the per-person accent colour; `/api/health` reporting the deployed version; the installable PWA shell; `da` and `en` from day one; the dosing-vocabulary test in CI. Food, meals and AI are absent: the tabs for them show a calm "comes in a later version" page, and a viewer gets the viewer shell with "Blodsukker vises ikke her" and the same placeholder for meals.

Hard rules first exercised here: a glucose value is never rendered without its age (`GlucoseValue` takes a reading with its timestamp, never a bare number); `viewer` never receives glucose, enforced in the API and in the Web PubSub group the token may join; every write goes through `emit()`; glucose sources are plugins behind `GlucoseSource`; no secrets in the repo (Key Vault + managed identity), no real people (fictional seed), no PII in logs (a logger that drops names and values); the dosing-vocabulary test runs on every PR; English in the repo, Danish only in `da.json`.

## v0.2.0 — Food and logging

The `foods` and `meals`/`meal_items` models; `lookup(spaceId, query | barcode)` resolving own library → shared cache → Open Food Facts → Frida → manual, with `off` and `frida` as `FoodSource` plugins and Frida imported as a static dataset at deploy; barcode scanning with the phone camera and a typed/USB-scanner field on desktop; portions as first-class chips ("1 skive", "½ skive", "Vej det"); photos in Blob Storage with thumbnails; the Library screen (phone list with tick-to-verify, desktop batch verify table and edit panel); verification (`verified: false` for anything from OFF, Frida or free text until a carer ticks it); logging a meal by scan, pick or typed text (no AI parsing yet) with the running carb total and "Gem måltid"; the simpleMode picker ("Hvad spiser du?" → "Ja, det spiser jeg") showing verified foods only; "Sidste måltid" on Now; and the viewer's day (today's meals and carb totals, no glucose). Events: `meal.created`, `meal.updated`, `meal.deleted`, `food.created`, `food.verified`.

Moved from the suggested cut: basic meal logging and the viewer's day come here rather than in v0.3.0, because the success criterion "the child finds her lunchbox herself" needs a meal to be saved, not only looked up, and because the viewer's day is only a list of meals once meals exist.

Hard rules first exercised: `verified: false` for OFF, Frida and free text, with `verifiedBy` on the verification path; `simpleMode` queries filter on `verified: true` and the person's own space; food sources behind `FoodSource`, nothing Danish hard-coded outside the plugins; photos stored only when the user saves; `meal_items` snapshot name and carbs so later food edits do not rewrite history.

## v0.3.0 — Meals on the curve

Meal detail with the glucose curve from −1 h to +4 h, the meal line and the bolus triangle, the same dish's previous curves faintly behind; deterministic statistics in code (peak, time to peak, time in range over the next 3 h, bolus-before-meal minutes) shown as `StatTile`s; the desktop compare view ("Sammen med de sidste 5 gange" and the table); History as a day timeline of meals over the curve and the desktop week with per-day tiles and "Ugens tal"; the "Bolus givet nu" timestamp tap for carers (the only insulin concept in the product); "Gem som egen ret"; previous/next meal keyboard navigation. No AI text yet: the Observation blocks render only when v0.4.0 provides one.

Hard rules first exercised: `bolusTs` is a timestamp and nothing else (no units field exists on `meals`); statistics are computed in code from readings, never by a model; viewer gets meals and totals in History but no curve and no stats derived from glucose (API-level test).

## v0.4.0 — AI

The `AiProvider` interface with `complete()`, `vision()`, `embed()` and the `anthropic`, `azure-openai` and `ollama` adapters; per-space on/off and provider in Settings; embeddings on `foods` and semantic search ("det brune brød" finds rugbrød), with OFF names normalised once at import; natural-language and voice logging that calls `lookup()` per item and returns a structured meal the user confirms line by line; photo → estimate labelled "Et gæt · ikke tjekket" with the simpleMode "Spørg en voksen" push to carers and carer correction; the insight sentence on meal detail and the weekly "Spørgsmål til klinikken", narrating statistics computed in v0.3.0; the per-space daily cap; the evals under `evals/` (Danish meals with photos, free-text parses) run in CI when prompts change and at every release.

Hard rules first exercised: raw readings never go to a model (the insight call receives the statistics object only, asserted by a test on the provider boundary); photos and text go to AI only from an explicit tap; everything AI touched is `verified: false`; the output schemas have no dosing field and the dosing-vocabulary test runs on generated insight text; the daily cap exists on the one call path.

## v0.5.0 — Community and portability

The `nightscout` and `manual` glucose sources behind the same interface (manual: finger-prick entry for people without a CGM); "send the correction to Open Food Facts" behind a question, with app name "Frejsi"; `CONTRIBUTING.md` and an architecture note; "deploy your own in 15 minutes" documented end to end from a fork (Bicep, one GitHub Action, `.env.example`); Docker Compose for non-Azure users if it can be done without a second code path (SQL Server container, local Web PubSub substitute); managed-identity authentication to Azure SQL replacing the Key Vault-held password if the driver supports it by then; a `FoodSource` plugin guide so `usda`, `bls`, `matvaretabellen` can be added by others.

Hard rules first exercised: nothing Danish is hard-coded is proven by a second source and a second deploy path; OFF contribution is never automatic.

## Later (unscheduled)

Pump data if a real-time API appears; official Dexcom API as an adapter if its EU delay drops; push notifications beyond "ask an adult"; data export ("Data og eksport" in the desktop Settings sidebar); the Nightscout-compatible read API so existing tools can follow Frejsi.
